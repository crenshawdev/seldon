# Phase 4: The architecture spine - Context

Gathered: 2026-11-17
Feeds: /cad-plan 4

## Scope boundary

In: The spine step of `/seldon`. It reads `brief.md` and `prd.md`, asks the trust-boundary, unattended-work and failure questions only for parts the design has, and writes `.planning/seldon/spine.md`: decisions of the six kinds ARCH-01 names, each with an `S-01` ID, a `Kind:` line and a quote or tag, checked by a new `--spine` mode. Also in: the spine rerun, the full architecture document written only on request, the routes that reach the spine step on resume, and the eval cases that prove each of these, with `spine-later` and `resume-later` rewritten.
Out: The epics step and the epics rerun (phase 5). An existing project's conventions recorded in the spine (ARCH-03, phase 6). Showing what a PRD change conflicts with, and walking spine and epics again after one (CHECK-03, CHECK-04, phase 6). The readiness check (phase 7). Any change to SKILL.md's `allowed-tools` or the README's eval grant. The Cadence-side reader of `.planning/seldon/`.
Deferred: None
Plan shape: multiple plans - planning splits the work into several plans inside this phase.

## Durable decisions

- D-01 (kind marker): Each spine decision carries a `Kind:` body line naming exactly one of the six kinds: design approach, boundaries, how state changes, who owns shared data, stack, hosting. The new `--spine` check enforces it and fails closed, so a seventh kind is caught when the spine step writes it, not only in an eval. A spine doesn't have to use all six. `docs/FORMAT.md` documents the line as part of the contract. Rejected: the kind word at the start of the heading, graded only by an eval regex, and no marker at all, whose grader could pass with the behavior missing (phase 3 D-21). Evidence: `docs/FORMAT.md` (lines 112-122: no kind today); `lib/check.mjs` (line 108: any heading text passes); `.planning/REQUIREMENTS.md` ARCH-01; the analyzer's probe (a `Kind: stack` line passes today's full check).
- D-02 (ARCH-02 parts): Outside input is anything typed or sent by people or systems the project doesn't control: users, members, the public, another service. The operator's own data, such as a file the owner maintains, isn't. Unattended work is anything the system does with no person present, such as a scheduled job. A design with outside input gets the trust-boundary question. A design with unattended work gets the unattended-work question and the failure question, and the failure question goes only with unattended parts. The answers, including who is told when the part breaks and how, go into that part's own S- decision, never into a decision of a new kind. Rejected: also asking the failure question about outside dependencies such as an email provider. Evidence: `.planning/ROADMAP.md` phase 4 criteria 2 and 3; `.planning/REQUIREMENTS.md` ARCH-01, ARCH-02; `samples/prd.md` (LOAN-03 is unattended, CAT-02 takes outside input); `.planning/CAPTURE.md` (the phase 4 who-is-told todo).
- D-03 (quotes in the spine): The spine follows the quote-or-tag rule. A decision drawn from source words has a `> ` quote directly under it, taken word for word from the brief's `> ` lines, keeping any design-file line under them, or from the user's replies to the spine step's own questions. A decision with no source words carries `[ASSUMPTION]` in its body, never in the heading. `docs/FORMAT.md` gains an "In the spine" subsection. Evidence: `.planning/CAPTURE.md` (the phase 4 verbatim-answers todo); `docs/FORMAT.md` (lines 194-246); phase 2 D-18; phase 3 D-13.
- D-04 (spine rerun): `/seldon spine` over an existing `spine.md` is a rerun, the way the PRD rerun works. It reads the previous spine first, changes it with Edit only, keeps every decision the change doesn't touch byte-identical, lists a dropped decision's ID on a prose `Retired: S-03, ...` line under the title, and never reuses a retired ID. `docs/FORMAT.md` gains that line for the spine. Rejected: deferring the rerun to phase 6. Evidence: `.planning/REQUIREMENTS.md` FLOW-03; `docs/FORMAT.md` (lines 160-175: `Retired:` is defined for the PRD only); `skills/seldon/SKILL.md` (the PRD rerun, lines 506-536); phase 3 D-03, D-09.
- D-05 (full architecture document): Seldon writes a full architecture document only when the user asks, to one fixed file, `.planning/seldon/architecture.md`. It expands on the spine's decisions by S- ID, drawing on the brief, the PRD and the spine, adds no decision of its own, and gets no check. `/cad-context` locks only S- IDs, so a document holding its own decisions would be a second, unlocked source a planner could follow against the spine. `docs/FORMAT.md`'s "exactly four files", the README's "four files" and SKILL.md's rule on which files Seldon writes change to name it as the one file written on request. Rejected: a FORMAT.md-defined shape with its own check. Evidence: `.planning/REQUIREMENTS.md` ARCH-04 and its Out of Scope row; `docs/FORMAT.md` (lines 7-14); `README.md` (line 13); `skills/seldon/SKILL.md` (lines 25-27); `lib/check.mjs` (lines 207-210: the full check ignores extra files).

## Decisions

- D-06 (what the spine step reads): The spine step reads `brief.md` and `prd.md` and nothing else: not `docs/design/`, not the dump, not the conversation. The one thing it takes from the conversation is the user's answers to its own questions. Stack and hosting words the user said reach it only through the brief's `> ` quotes, since the PRD leaves them out. Evidence: `.planning/REQUIREMENTS.md` FLOW-04; `skills/seldon/SKILL.md` (lines 455-460, 619-622); phase 3 D-14, D-15.
- D-07 (where a run starts): With a brief and a PRD, no spine and an empty argument, Seldon says a fixed resume line before any tool call. The line names `prd.md` and says `/seldon prd` revises it, and the spine step follows. With a brief, a PRD and a spine, a bare `/seldon` ends on a reworded later-release line that names only epics. `/seldon spine` runs the spine step, and with no PRD there it writes nothing and says so. `/seldon epics` still writes nothing. Today's "The spine and epics steps come in a later release" line is retired from every shipped file. Evidence: `skills/seldon/SKILL.md` (lines 46-48, 140-141, 167-184, 484-504); phase 3 D-01, D-06, D-17.
- D-08 (routes that stopped on a PRD): A "go on" answer to the documents question, with a brief and a PRD there, resumes at the spine step the way a bare `/seldon` does. The PRD step's create guard ends on its own fixed line pointing to `/seldon prd`, separate from any later-release wording. Evidence: `skills/seldon/SKILL.md` (lines 136-143, 484-504).
- D-09 (spine questions): The spine step asks every open question in one plain-prose turn and writes nothing in that turn, as the PRD step does. A new "Spine questions answered" route in section 1 carries the answers back into the spine draft, so this stop point has a way back to its own step. The trust-boundary, unattended-work and failure questions use fixed words, each on a line of its own, as "Who is it for?" does, so a positive regex and a `not_contains` regex both test them honestly. Evidence: `skills/seldon/SKILL.md` (lines 110-114, 297-302, 471-473); phase 3 D-07, D-19, D-21; `.planning/phases/3/SUMMARY.md` (deviation: three stop points with no route back).
- D-10 (check mode): `lib/check.mjs` gains `--spine`, which reads only `spine.md` and passes with `seldon check: spine.md conforms`, beside `--brief` and `--prd`. It enforces D-01's `Kind:` line on top of the existing heading, ID and body rules. The usage string, FORMAT.md's "The check" section and the Node tests change with it. Evidence: `lib/check.mjs` (lines 220-238); `tests/check.test.mjs` (line 163); phase 3 D-10. The analyzer's probe: `--spine` exits 2 today.
- D-11 (IDs): Decision IDs stay `S-01` style in a `## S-01: <decision>` heading with a non-empty body, as phase 1 D-03 locked and `lib/check.mjs` enforces. Evidence: `docs/FORMAT.md` (lines 112-122); `lib/check.mjs` (lines 16, 105-131).
- D-12 (sample spine): `samples/spine.md` stays the one conforming Toolshed spine and is updated in place with `Kind:` lines and quotes or tags. S-01 to S-03 keep their IDs, since `samples/epics.md` cites them, and any added decision takes the next number. Evidence: `samples/spine.md`; `samples/epics.md` (lines 11, 22, 30); phase 3 D-20.

SKILL.md's `allowed-tools` stays phase 2 D-02's five entries, and the README eval command keeps its two `--allow-tools` rules. `spine.md`, `architecture.md` and the `--spine` command fall inside the existing `Edit(.planning/seldon/**)` rule and the check's Bash rule. ## Acceptance criteria

- [ ] AC1: A spine case (a scaffold copies a brief and PRD pair whose brief states stack and hosting, with no unattended work and no outside input; prompt a bare `/seldon`) opens with the fixed resume line naming `prd.md`, creates `.planning/seldon/spine.md`, and repeats `seldon check: spine.md conforms` from the `--spine` mode. A file regex finds every decision with an `S-NN` heading and a `Kind:` line naming one of the six kinds, and every decision carries a `> ` quote or an `[ASSUMPTION]` tag.
- [ ] AC2: Two replays. A design with a scheduled job gets the fixed unattended-work question and the fixed failure question, and writes nothing that turn. A design with no unattended work gets neither (`not_contains` on both fixed lines).
- [ ] AC3: Two replays. A design that takes outside input gets the fixed trust-boundary question. One whose only input is the operator's own data doesn't get it (`not_contains`).
- [ ] AC4: A replay that answers the spine's questions writes `spine.md`, and the job's own S- decision carries the user's answer, including who is told when it breaks and how, as a `> ` quote.
- [ ] AC5: A spine case that doesn't ask for the full document makes no Write or Edit to any `.planning/seldon/` path but `spine.md`. A case that asks for it creates `.planning/seldon/architecture.md`.
- [ ] AC6: `/seldon spine` over an existing `spine.md` (a scaffold copies a brief, a PRD and a spine, with the PRD changed so one decision no longer applies) keeps every untouched decision byte-identical, lists the dropped S- ID on a `Retired:` line, and doesn't reuse it.

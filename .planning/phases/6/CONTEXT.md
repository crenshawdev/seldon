# Phase 6: Existing projects and design folders - Context

Gathered: 2026-11-17
Feeds: /cad-plan 6

## Scope boundary

In: `/seldon` on a project already under Cadence. FLOW-05: a run where `.planning/PROJECT.md` exists starts a walk for the next body of work, writing only inside `.planning/seldon/`. Design folders: a new body of work goes in `.planning/seldon/<name>/` beside a design already at the top of `.planning/seldon/`, Seldon asks for the folder's name, and it asks which design when more than one exists. ARCH-03: on a project under Cadence the spine step reads the existing code, records its conventions as decisions with stable IDs, and asks who relies on what today. `docs/FORMAT.md`'s Location and "In the spine" sections, `README.md`, and the eval cases that prove each of these.
Out: The readiness check and the handoff command, including which Cadence command a design folder is handed off with (the readiness and handoff phase). Run-wide graders and `/cad-verify` running the whole suite (the full graders phase). The Cadence-side reader of `.planning/seldon/`. Any change to SKILL.md's `allowed-tools` or the README's eval grant. Reading Cadence's planning files at the brief or PRD step.
Deferred: "PRD changes flow downstream" (CHECK-03, CHECK-04), split off by the size check as its own phase after this one, added through `/cad-phase insert`, because the two halves share almost nothing and together would have run larger than phase 5. Its confirmed rulings carry into that phase's context. When `/seldon prd` changes the PRD and `spine.md` exists, the rerun also reads the spine, only to name conflicts, and nothing from it enters the PRD. A decision conflicts when the change alters or drops something it states or quotes, and epics citations aren't used for this. The conflict report is a stop point before any Edit, ending on a fixed question with its own section 1 route, and a decline writes and edits nothing. Changes named at the PRD's confirm question after a rerun count as PRD changes too. Revision stamps: `brief.md`, `prd.md` and `spine.md` each carry a revision, and `prd.md`, `spine.md` and `epics.md` each record the revision of the document they were built from. A rerun bumps only its own revision, so no step writes another step's file. `lib/check.mjs` works out what is stale from the stamps, which narrows phase 5 D-12 to ID cross-references. One mechanism covers brief to PRD, PRD to spine and spine to epics, and only a PRD change gets the conflict report. Any applied PRD change makes the spine stale. The rewalk is the existing rerun, reached from a bare `/seldon` through a fixed resume line, and the epics rewalk doesn't read Cadence's roadmap. Its criteria as drafted: a `/seldon prd` rerun dropping LOAN-03 names S-03 before any Write or Edit and a declining replay writes nothing; `lib/check.mjs` reports each stale link from the stamps; replays after an applied change walk the spine and then the epics again; and the suite gate.
Plan shape: split - deferred slice above. What stays is several plans inside this phase, and plans that share `skills/seldon/SKILL.md` run in order.

## Durable decisions

- D-01 (under Cadence): A project counts as under Cadence when `.planning/PROJECT.md` exists, the same file Cadence's `/cad-new-project` stops on, so Seldon and Cadence can never disagree about it. The readiness and handoff phase reuses the same test to choose between `/cad-new-project` and `/cad-phase` or `/cad-milestone`. Roadmap phase 6's success criteria say "a Cadence roadmap"; this deviates from that wording on purpose, and the eval cases seed `PROJECT.md` and `ROADMAP.md` both. Rejected: keying on `.planning/ROADMAP.md`, which tells a half-initialized project (PROJECT.md, no ROADMAP.md) to run a command that refuses. Evidence: `/code/cadence/cadence-core/workflows/new-project.md` line 36; `.planning/ROADMAP.md` lines 76 and 89; owner's ruling.
- D-02 (design folders): Each new body of work gets its own design folder, `.planning/seldon/<name>/`, holding the same four files under the same format. `docs/FORMAT.md`'s Location section, section 2's routes and the fixed resume and guard lines name the folder a run works in. Rejected: one live design that the user moves aside by hand, and rerunning the existing documents in place for new work, which retires IDs that built phases came from. Evidence: `skills/seldon/SKILL.md` line 9 (`Edit(.planning/seldon/**)` covers subfolders); `lib/check.mjs` lines 248-262 (every mode takes any directory); `.planning/CAPTURE.md` (the phase 6 design-already-there todo); `/code/cadence/.planning/seldon/` (holds `brief.md` and `prd.md`); a `git grep` for `planning/seldon` in `/code/cadence` outside `.planning` found no reader yet; owner's ruling.
- D-03 (the top-level design): A design already at the top of `.planning/seldon/` stays there and works as it does today. Only a new body of work goes in a named folder. Rejected: moving every design into a named folder, which breaks the layout every existing design, sample and eval case uses. Evidence: `/code/cadence/.planning/seldon/`; `samples/`; `evals/`; owner's ruling.
- D-04 (naming a design): When a new body of work starts and a design already exists, Seldon asks for a short folder name in fixed words and writes nothing in that turn. The reply routes back through section 1. A name is lowercase letters, digits and hyphens. Rejected: a name Seldon derives from the dump. Evidence: phase 3 D-02 (a dump while documents exist is asked about, never set aside); phase 3 SUMMARY (every stop point needs a route back); owner's ruling.
- D-05 (choosing a design): With more than one design, any run that needs one, bare or a step name, first asks which design in fixed words, and the answer routes back to the step it was going to run. With one design it doesn't ask. Phase 3 D-08's argument grammar stays as it is. Rejected: extending the grammar to `/seldon <name> <step>`. Evidence: phase 3 D-08; phase 3 SUMMARY (routes back); owner's ruling.
- D-06 (the spine reads code): On a project under Cadence, the spine step reads the existing code outside `.planning/` as well as `brief.md` and `prd.md`. This amends phase 4 D-06 and section 15's "Read those two files and nothing more" for that case only. FLOW-04's "documents" are Seldon's documents, so the code counts as project input, the way a design folder does for the brief. Rejected: the brief step reading the code and passing conventions on through its quotes, which forces them into a brief section that has no place for them. Evidence: `.planning/phases/4/CONTEXT.md` (D-06; ARCH-03 deferred to phase 6); `skills/seldon/SKILL.md` lines 733-743; `.planning/REQUIREMENTS.md` FLOW-04, ARCH-03; `.planning/ROADMAP.md` line 77; `lib/check.mjs` line 12 (the brief's eight sections are fixed).
- D-07 (quoting code): A convention read from code meets the quote-or-tag rule as a word-for-word quote from the file, with a `(path)` source line under it, the way design-folder words are quoted. `docs/FORMAT.md`'s "In the spine" adds the existing code as a third quote source. `lib/check.mjs` doesn't change for it. Rejected: tagging conventions `[ASSUMPTION]`, which marks what the code shows as a guess. Evidence: `docs/FORMAT.md` lines 257, 285-295, 326-331; `lib/check.mjs` lines 131-147.
- D-08 (six kinds): Conventions keep the six kinds. Each convention recorded takes one of them, and a convention that fits none stays out of the spine. Rejected: a seventh `convention` kind across the check, the format, the tests and the samples. Evidence: `lib/check.mjs` line 15 (`KINDS`) and lines 142-145; `docs/FORMAT.md` lines 134-148; phase 4 D-01.
- D-09 (who relies on what): On a project under Cadence, the spine step always asks who relies on what today, in fixed words on a line of its own, with its own section 1 route. Each answer is recorded under the spine decision for the part it names. Rejected: never asking, which leaves dependents outside the repository invisible, and asking only when the code shows a public interface. Evidence: `.planning/CAPTURE.md` (the FLOW-05 and ARCH-03 todo); phase 4 D-09 (fixed-word spine questions with a route back); owner's ruling.

## Decisions

- D-10 (no refusal to remove): Seldon has no refusal to remove. Every `.planning/` path in SKILL.md is under `.planning/seldon/`, and a run with no design already goes to the dump. FLOW-05's work is a SKILL.md statement that files in `.planning/` outside `.planning/seldon/` don't change where a run starts, plus the eval proof. The refusal FLOW-05 names is Cadence's own. Evidence: `skills/seldon/SKILL.md` section 2 (lines 215-224); `/code/cadence/cadence-core/workflows/new-project.md` line 36.
- D-11 (brief and PRD inputs): The brief and PRD steps read no Cadence planning file on a project under Cadence. The dump describes the next body of work, and existing-project knowledge enters the design only at the spine. Evidence: `skills/seldon/SKILL.md` section 4 line 299 ("Look nowhere else") and section 12 lines 535-540; phase 3 D-15.
- D-12 (which conventions): The spine records only conventions that touch a part this body of work builds, or that are project-wide (design approach, stack, hosting), because phase 5 D-09 needs every S- ID cited by at least one epic. Evidence: `skills/seldon/SKILL.md` lines 766-767 and 1089-1090; phase 5 D-09.
- D-13 (settled by the code): On a project under Cadence, a stack or hosting choice the code settles counts as settled and isn't asked about, even when the brief never quotes it. Evidence: `skills/seldon/SKILL.md` lines 776-779.
- D-14 (permissions): No grant changes. SKILL.md's `allowed-tools` stays phase 2 D-02's five entries, and reading the code and Cadence's files falls inside `Read`, `Glob` and `Grep`, and writing a design folder inside `Edit(.planning/seldon/**)`. Evidence: `tests/skill.test.mjs` lines 11-17; `README.md` line 62; phase 4 D-13; phase 5 D-18.
- D-15 (Cadence-project fixtures): The Cadence-project fixture lives under `samples/<case>/`: Cadence's planning files and a small code tree, copied in by a `seed.sh` using `mkdir -p` and `cp -R`. "Every Cadence file byte-identical" is graded by no Edit, plus no Write outside the design folder the run writes, as `design-folder` does. Evidence: `tests/scaffold.test.mjs` lines 20-30; `evals/design-folder/graders/no-edit.md` and `no-write-outside.md`; phase 3 D-21.
- D-16 (proving conventions): The spine case's code fixture carries one distinctive token found only in the code, never in the seeded brief or PRD, and a file regex checks that it sits under an `## S-NN:` heading. With D-09 the case is a history replay that carries the who-relies answers. Evidence: `evals/design-folder/graders/names-design-fact.md`; `evals/full-walk/case.yaml` (history plus scaffold); phase 3 D-21.
